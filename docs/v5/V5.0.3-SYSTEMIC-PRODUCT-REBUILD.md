# GoJet V5.0.3 — Systemic Product Rebuild

Status: **ACTIVE / release blocked**

Base: `052ed0c58d0ce4fc509c8f45e80410ded59f26cc`

This rebuild is not a copy-polish patch. It reopens the customer-facing product, Admin, Workspace, runtime observability and release gates after the v5.0.2 test-install package exposed systemic product defects.

## Release rule

No v5.0.3 test-install package may be presented as ready until all of the following are true on the same exact HEAD:

1. Site, Auth, Workspace, Admin and Docs pass `zh-CN` and `en` browser audits with no unintended language mixing.
2. Visible product copy contains no internal implementation language such as database/cache/redirect-plane/server-authority terminology.
3. Admin overview and Workspace overview load real server data automatically and expose honest loading/error/empty states.
4. Admin settings expose the configuration already supported by the server, including brand assets, general site metadata, payment providers and Turnstile.
5. Announcements are editable lifecycle objects: create, edit, enable/disable, schedule and delete.
6. Workspace account settings provide an actionable email-verification flow.
7. Destination-risk state is reflected in the customer link status; a link under review must never be presented as unconditionally healthy.
8. Service status is backed by real runtime heartbeat/version evidence. Synthetic `unknown` rows are not accepted as observability.
9. Top-level shell controls are functional or absent. Decorative dead Search/Help/Notification/Profile controls are forbidden.
10. Full frontend checks, Go tests, Native package verification and authenticated fixed-viewport browser gates pass.

## Blocking defect ledger

### A. Localization and product copy

- Global Site, Admin and Workspace contain mixed Chinese/English surfaces even when `简体中文` is selected.
- The previous visible-locale verifier could accept hard-coded English if the same literal existed in a global translation registry. That permitted source-level English to survive and depend on runtime DOM rewriting.
- Runtime DOM translation is not accepted as the primary localization contract for production UI. Production visible copy must be selected explicitly from the active locale at render time.
- Customer surfaces must not contain internal engineering phrases (`MySQL`, `Redis redirect plane`, `server-authoritative`, `control plane`, etc.) unless the page is explicitly developer/operations documentation.

### B. Admin

- Overview initially renders empty metric dashes despite real users/workspaces/links.
- Payment transactions exist without an Admin payment-channel/provider configuration surface.
- Plan editing is an oversized engineering form and is not consistently localized.
- Service status reports seven services as unknown because the backend does not consume real heartbeat evidence.
- Announcements lack normal edit/delete/enable/schedule management.
- General settings expose only a small fraction of the server-supported settings; logo/favicon/site metadata are missing from the UI.
- Turnstile is read-only despite server support for site key, write-only secret, hostnames and per-flow switches.
- Mail settings and mail templates are mixed-language.
- Destination-risk review uses internal/ambiguous language and does not explain the effect of allow/review/block.

### C. Workspace

- Overview is an instruction page instead of an operational dashboard, despite `/api/workspaces/{id}/overview` already returning live metrics, usage, trend, recent links and anomalies.
- Settings contains mixed-language tabs/content and shows `Verification required` without an actionable send-verification flow.
- Billing is mixed-language.
- Link create/edit surfaces expose implementation details and mixed-language form labels.
- Link detail displays the raw active status as healthy while the destination-risk decision is `review`.

### D. Website / shell

- Locale selection does not consistently produce a localized navigation/content tree in the installed build.
- Hero/nav content contains redundant labels and inconsistent customer wording.
- Product shell renders controls that have no real action in the current product (fake command search, notification bell, unlinked profile avatar).

## Engineering gates introduced by this rebuild

### Explicit locale gate

Production TSX visible text must be explicitly localized at render time (`text(en, zh)` or an equivalent keyed localized primitive). A literal being present in a global dictionary is not sufficient.

### Product-copy gate

Customer-visible sources are scanned for internal implementation terms and known regression phrases from the test-install screenshots.

### State-integrity gate

Browser tests must assert semantic consistency, including:

- risk `review` => warning/review state, never green healthy;
- email unverified => visible verification action;
- overview APIs => populated real values when fixture/server data exists;
- configured settings => editable forms hydrated from server state;
- service status => heartbeat-derived evidence and version.

## Completion evidence

The final completion comment must include exact HEAD SHA, workflow run IDs, browser locale screenshots/evidence, Go/frontend test results, Native package verification and the generated test-install artifact name. A green build without these product-state assertions is not release evidence.
